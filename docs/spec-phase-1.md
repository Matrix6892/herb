# Витрина для iHerb. Спецификация фазы 1 для агентов-разработчиков

Версия 1.0 от 26.09.2026. Основание: документ «Продуктовый вижн: рациональная витрина для iHerb» и рабочий документ «Проект, фаза 1, техтребования, регистрация, локализации» (далее «рабочий документ»).

> Файл сохранён в репозитории как источник требований для агентов. Решения
> отсюда оформлены как ADR 0001–0012 в `docs/adr/`; допущения, сделанные при
> реализации, — как ADR 0013 и далее; открытые вопросы — в
> `docs/open-questions.md`; задачи — в `docs/backlog.md`.

## 0. Как читать и применять этот документ

Каждое решение здесь записано в четырёх частях:

| Часть | Что в ней | Как использовать |
| --- | --- | --- |
| Решение | Что делаем | Выполнять как есть |
| Почему | Предпосылки из прошлого: факты, правила, ограничения, из которых решение следует | Если предпосылка оказалась неверной, остановиться и сообщить владельцу; решение может быть пересмотрено |
| Для чего | Что это решение должно обеспечить в будущем: фазы 2–4, локализации, масштаб | При выборе между двумя допустимыми реализациями выбирать ту, которая лучше служит «для чего» |
| Границы | Что нельзя менять без владельца | Нарушение границы блокирует PR |

Правила поведения агента:

1. Инварианты раздела 1 сильнее любой локальной оптимизации. Если задача требует нарушить инвариант, задача формулируется неверно; остановиться и спросить.
2. Неизвестное не заменяется допущением молча. Открытые вопросы перечислены в разделе 12 с дефолтом на случай отсутствия ответа. Любое новое допущение записывается в `docs/adr/` по шаблону раздела 10 и помечается `status: assumed`.
3. Простота важнее общности. Фаза 1 обслуживает одну категорию и один язык; абстракции создаются только там, где раздел «Для чего» прямо требует их для фаз 2–4.
4. Всё воспроизводимо: сборка сайта из репозитория и снимка данных даёт байт-в-байт тот же результат.

## 1. Инварианты продукта

Эти правила следуют из условий партнёрской программы iHerb, правил Chrome Web Store, принципов документа и решений владельца. Они не обсуждаются в PR.

| № | Инвариант | Почему | Для чего |
| --- | --- | --- | --- |
| И1 | Программа никогда не читает страницы iherb.com. Единственные источники данных: товарный фид партнёрской сети и ручной ввод с этикеток | Условия iHerb запрещают скрейпинг; живой прокси отвергнут в документе; нарушение ведёт к отключению от программы, то есть к потере единственного дохода | Продукт переживает смену вёрстки iHerb и не зависит от защиты от ботов |
| И2 | Ранжирование не зависит от размера комиссии. Ставка не входит ни в одну формулу и ни в один тест | Доверие названо единственным активом продукта | Тот же код ранжирования работает для второго и третьего магазина в фазе 4 |
| И3 | Кнопка «Buy on iHerb» ведёт по трекинговой ссылке сети напрямую. Никаких собственных редиректов, скрытых переходов, подмены чужих кодов и cookie | Условия программы запрещают редиректы и замаскированные ссылки; правила Chrome Web Store 2025 требуют действия пользователя | Расширение браузера в фазе 4 использует ту же кнопку без переделки |
| И4 | Рядом с каждой кнопкой покупки, выше линии сгиба, текст раскрытия комиссии | Требование FTC и условий программы | Тот же компонент используется во всех локализациях |
| И5 | Никаких медицинских рекомендаций. Продукт показывает дозы и цены; дозу приносит пользователь | Юридический риск и принцип документа | Стек и верхние допустимые уровни в фазе 3 остаются информированием, не советом |
| И6 | Без аккаунтов, без сторонних рекламных трекеров, без cookie в фазе 1 | Принцип приватности документа; стек и дозы названы чувствительными данными | Стек в фазе 3 хранится локально и в ссылке |
| И7 | Неизвестное показывается как неизвестное: нет цены, нет рейтинга, нет состава. Нули и заглушки вместо неизвестного запрещены | Принцип «честность в мелочах» | Кнопка «ошибка в данных» и уверенность полей в фазе 2 опираются на ту же модель |
| И8 | Домен и визуальный стиль не похожи на iHerb; слова «iherb» и «herb» в домене отсутствуют | Условия программы запрещают товарные знаки в домене | Бренд переживает добавление других магазинов |
| И9 | Юридическое лицо, хостинг и аккаунты сетей находятся вне России и Беларуси | Условия программы и правила выплат Impact | Выплаты и доступ к сетям не прерываются |
| И10 | Доставка в Россию не поддерживается ни в интерфейсе, ни в ссылках, ни в локализации | Решение владельца | Продукт мировой, английский первым |

## 2. Что строим в фазе 1

Решение. Статический англоязычный сайт на одну категорию с тремя экранами: категория `/c/<slug>`, товар `/pr/<slug>/<id>`, методика `/how`. Три пресета сортировки: `cheapest_per_unit`, `fair_rating`, `balance`. Кнопка покупки с раскрытием. Кнопка «ошибка в данных». Ежедневное обновление цен. Аналитика: просмотры, клики «Buy», возвраты за 30 дней.

Почему. Документ определяет MVP именно так; критерии успеха фазы 1: не менее 3 000 посетителей, не менее 15% кликов «Buy» среди посетителей выдачи, не менее 50 заказов по отчётам сети, не менее 20% вернувшихся за 30 дней. Всё, что не нужно для проверки этих критериев, в фазу 1 не входит.

Для чего. Ядро (модель данных, нормализация, скоринг) переходит в фазы 2–4 без переделки: категории, гибридные фильтры, эквиваленты, история цен, алерты, стек, второй магазин.

Границы. Нельзя добавлять в фазу 1: ввод своей дозы, историю цен в интерфейсе, эквиваленты, алерты, PWA, бот, поисковые страницы, вторую категорию, вторую локализацию.

## 3. Язык и архитектура

### 3.1 Rust как основной язык

| | |
| --- | --- |
| Решение | Всё ядро, конвейер данных, генератор сайта и сервис API пишутся на Rust (stable, edition 2024). Один cargo workspace |
| Почему | Главный риск продукта: ошибка в дозе или пересчёте на видном месте. Строгие типы для единиц измерения, отсутствие неявных преобразований и детерминированная арифметика снижают этот риск сильнее, чем тесты поверх динамического языка. Ежедневная задача и API должны жить на дешёвом хостинге без обслуживания: один бинарник без рантайма. Владелец ведёт разработку на Rust в других проектах |
| Для чего | В фазе 3 появляются оптимизатор корзины и посылок и расчёт суммарных доз по стеку; это вычислительные задачи, для которых ядро уже будет типизировано. В фазе 4 ядро должно работать в расширении браузера через WebAssembly: `catalog-core` с первого дня компилируется под `wasm32-unknown-unknown` без изменений |
| Границы | Никаких вторых реализаций расчётов на другом языке. Одна формула живёт в одном месте: `catalog-core` |

### 3.2 Где другие языки выигрывают

| Язык | Где | Почему | Границы |
| --- | --- | --- | --- |
| Python | `tools/label-assist/`: черновой разбор фото этикеток через LLM и OCR для помощи ручному вводу. Разовые исследования данных (ноутбуки в `research/`) | Экосистема LLM, OCR и анализа данных; код одноразовый, требования к надёжности низкие | Выход инструмента: JSON по схеме из `catalog-core`, который человек проверяет и импортирует. Python не пишет в базу и не участвует в ежедневной задаче |
| JavaScript в браузере | Несколько сотен строк без сборщика: переключение пресета из адреса страницы, отправка события клика, форма «ошибка в данных» | Первая отрисовка должна укладываться в секунду на телефоне; фреймворк и сборка не дают выигрыша на трёх экранах | Без TypeScript, без бандлера, без внешних библиотек в фазе 1. Страница полностью читаема без JavaScript |
| SQL | Схема и миграции SQLite | Декларативная схема проверяется отдельно от кода | Миграции только вперёд, нумерованные |
| HTML и CSS | Шаблоны | Статика | Один CSS-файл до 30 КБ |

### 3.3 Структура workspace

```
Cargo.toml                 workspace
crates/
  catalog-core/            домен, единицы, нормализация, скоринг; без IO; собирается под wasm
  catalog-store/           схема SQLite, миграции, репозитории
  feed-ingest/             чтение фида сети, сопоставление с каталогом, снимки цен
  site-gen/                генерация статического сайта из снимка
  edge-api/                axum: события кликов, отчёты об ошибках
  ops-cli/                 команда `vitrina`: ingest, build, publish, verify, import-labels
tools/label-assist/        Python, черновой разбор этикеток
data/
  reference/               справочник веществ и форм (TOML), с источниками
  labels/                  ручной ввод состава по товарам (TOML), с датой и автором проверки
  fixtures/                контрольные наборы для тестов
site/
  templates/               askama
  static/                  CSS, JS, иконки
docs/adr/                  решения по шаблону раздела 10
```

Почему такое разбиение. `catalog-core` без IO, чтобы тестировать формулы на чистых данных и компилировать в WebAssembly. `feed-ingest` отделён от `catalog-store`, потому что формат фида меняется сетью и должен ломать только один крейт. `site-gen` читает только снимок, чтобы сборка была воспроизводима.

Для чего. В фазе 2 добавляются крейты `price-history` и `alerts`, в фазе 3 `stack-optimizer`, все поверх `catalog-core`. В фазе 4 `catalog-core` идёт в расширение.

## 4. Модель данных

### 4.1 Единицы и числа

| | |
| --- | --- |
| Решение | Массы хранятся в микрограммах как `u64` (тип `Mass`), деньги в центах USD как `i64` (тип `Money`), количества как `u32`. Отношения (коэффициент соли к элементу) как рациональные числа `Ratio { num: u32, den: u32 }`. Плавающая точка появляется только на последнем шаге: расчёт оценок 0–100 и вывод на экран |
| Почему | Ошибка пересчёта единиц названа главным риском. Целые микрограммы покрывают диапазон от 1 мкг (витамин B12) до 10 г (порошки) без потери точности. МЕ хранится отдельным типом `IU` с явной конверсией через справочник, потому что коэффициент зависит от вещества (витамин D: 40 МЕ = 1 мкг; витамин A и E по своим правилам) |
| Для чего | Сумма доз по стеку в фазе 3 и сравнение с верхними допустимыми уровнями требуют точной арифметики без накопления ошибок |
| Границы | `f64` для доз и цен в хранилище запрещён. Конверсия МЕ без указания вещества запрещена на уровне типов |

### 4.2 Сущности

| Сущность | Ключевые поля | Источник | Примечание |
| --- | --- | --- | --- |
| `Substance` | `id` (например `magnesium`), названия, синонимы, единица по умолчанию, ссылка на источник | `data/reference/substances.toml` | Ручной справочник |
| `Form` | `id` (например `magnesium_glycinate`), `substance_id`, `elemental_ratio: Ratio`, `source_url`, `bioavailability_note` | `data/reference/forms.toml` | Коэффициент биодоступности хранится, но по умолчанию `k_form = 1`; включается пользователем в фазе 2 |
| `Product` | `iherb_id`, `slug`, `brand`, `title`, `category_id`, `label_ref`, `status` | Фид + ручной ввод | `slug` совпадает с путём iHerb, чтобы работала подмена домена |
| `Label` | `product_id`, `serving_size: u32` (капсул на порцию), `servings_per_container: u32`, `ingredients: Vec<LabelLine>`, `verified_by`, `verified_at`, `label_photo_ref` | `data/labels/<iherb_id>.toml` | Одна этикетка на товар; смена формулы создаёт новую запись с датой |
| `LabelLine` | `form_id`, `declared_mass: Mass`, `declared_as: SaltMass \| ElementalMass \| IU`, `confidence: Verified \| Recognized \| Unknown` | Ручной ввод | `Unknown` исключает товар из сравнения |
| `PriceSnapshot` | `product_id`, `date`, `price: Option<Money>`, `in_stock: bool`, `hidden_until_cart: bool`, `feed_row_hash` | Фид | Ежедневно; отсутствие цены хранится как `None`, не как 0 |
| `RatingSnapshot` | `product_id`, `date`, `avg: Option<f32>`, `count: Option<u32>` | Фид или разрешённый источник | Заполняется только в ветке A раздела 5.4 |
| `Category` | `id`, `slug`, `substance_id`, `unit_label` («per 100 mg magnesium») | Ручной | Одна в фазе 1 |
| `ErrorReport` | `product_id`, `field`, `text`, `created_at`, `page_url` | Пользователь | Без личных данных |
| `ClickEvent` | `product_id`, `preset`, `page`, `ts`, `session_hash` | Браузер | `session_hash` = хэш от user agent и дня, без cookie |

Почему. Разделение «что написано на этикетке» (`declared_as`) и «что мы посчитали» позволяет показать пользователю источник каждого числа и хранить уверенность по каждому полю. Смена формулы как новая `Label` с датой нужна для флага «формула сменилась» и для разделения отзывов до и после в фазе 3.

Для чего. `Form` с `bioavailability_note` и `elemental_ratio` со ссылкой на источник обслуживает страницу «справочник форм» фазы 2. `PriceSnapshot` по дням с первого дня накапливает историю цен для фазы 2, хотя интерфейс её не показывает.

### 4.3 Хранилище

Решение. SQLite, один файл, WAL. Миграции в `catalog-store/migrations/NNN_*.sql`. Снимок для сборки сайта: копия файла базы с датой в имени.

Почему. Одна категория: сотни товаров и тысячи строк цен в год. Один файл упрощает резервное копирование и воспроизводимость сборки. Postgres не даёт выигрыша до фазы 3.

Для чего. Репозитории в `catalog-store` пишутся за трейтами, чтобы в фазе 3 при необходимости перейти на Postgres, меняя один крейт.

Границы. Прямые SQL-запросы вне `catalog-store` запрещены.

## 5. Расчёты

Все формулы живут в `catalog-core::scoring` и дублируются словами на странице `/how`. Тест `how_page_matches_code` проверяет контрольные числа из этого раздела и на странице, и в коде.

### 5.1 Элементарная доза

Для строки этикетки с `declared_as = SaltMass`: `elemental = declared_mass × form.elemental_ratio`. Для `ElementalMass`: без изменений. Для `IU`: через таблицу конверсии вещества. Доза на порцию по веществу категории: сумма по строкам с этим веществом. Округление: вниз до микрограмма, один раз, в конце.

Почему. Этикетки пишут то массу соли, то элемент; документ приводит пример «цитрат магния 500 мг», где магния кратно меньше. Пользователь должен видеть, какое число взято с этикетки и каким коэффициентом умножено.

Для чего. Тот же код считает суммарную дозу по стеку в фазе 3.

### 5.2 Цена за эффективную единицу

```
P_unit = price / (servings_per_container × D_elemental × k_form)
```

`k_form = 1` в фазе 1. Единица вывода задаётся категорией (`unit_label`), например центы за 100 мг магния. Товар без цены, без проверенной этикетки или с `hidden_until_cart = true` не получает `P_unit` и в пресетах не участвует; на странице он показан с причиной.

Для чего. Цена в день на своей дозе в фазе 2 использует ту же `D_elemental` и формулу с округлением вверх числа капсул:

```
C_day = (price / N_caps) × ceil(D_target / D_cap)
```

### 5.3 Рейтинг с поправкой

```
R_b = (n × R + C × m) / (n + C)
```

`R` средняя оценка товара, `n` число отзывов, `m` невзвешенное среднее `R` по товарам категории с известным рейтингом, `C` медиана `n` по той же выборке. Пересчитывается при каждой сборке. Товар без рейтинга не получает `R_b`.

Почему. Документ: 5,0 на 8 отзывах не должна стоять выше 4,8 на 40 000.

### 5.4 Ветки по рейтингу

| Ветка | Условие | Что меняется |
| --- | --- | --- |
| A | iHerb разрешает показывать рейтинг и число отзывов, данные есть в фиде или разрешённом источнике | Пресеты: `cheapest_per_unit`, `fair_rating`, `balance` |
| B | Разрешения нет | Пресеты: `cheapest_per_unit`, `cheapest_verified` (только товары с флагом стороннего теста), `balance` не собирается. `RatingSnapshot` не заполняется |

Ветка выбирается владельцем до начала работы над `site-gen` (вопрос О2 раздела 12). Код `catalog-core` поддерживает обе ветки через `Option`.

### 5.5 Пресет «balance»

Оценки внутри категории по товарам, у которых есть и `P_unit`, и `R_b`:

```
q_price(x)  = 100 × (ln P_max − ln P_unit(x)) / (ln P_max − ln P_min)
q_rating(x) = 100 × (R_b(x) − R_min) / (R_max − R_min)
S(x)        = min(q_price(x), q_rating(x))
```

Порядок: по `S` убыв.; при равенстве в пределах 1e-9 по `q_price + q_rating` убыв.; затем по `P_unit` возр.; затем по `iherb_id` возр. Если в категории один товар с рейтингом, `q_rating = 100` для него. Если `P_max = P_min`, `q_price = 100` для всех.

Почему логарифм: документ требует считать по значениям, потому что разница в $0,01 и в $0,10 на ранговой шкале выглядела бы одинаково; логарифм делает равными относительные разницы цен.

Контрольный набор из документа (цены в $ за 100 мг, рейтинг уже с поправкой):

| Товар | P_unit | R_b | q_price | q_rating | S |
| --- | --- | --- | --- | --- | --- |
| A | 0,06 | 4,30 | 100,0 | 0,0 | 0,0 |
| B | 0,08 | 4,70 | 76,1 | 66,7 | 66,7 |
| C | 0,09 | 4,80 | 66,3 | 83,3 | 66,3 |
| E | 0,10 | 4,60 | 57,6 | 50,0 | 50,0 |
| D | 0,14 | 4,85 | 29,6 | 91,7 | 29,6 |
| F | 0,20 | 4,90 | 0,0 | 100,0 | 0,0 |

Ожидаемый порядок `balance`: B, C, E, D, A, F (у A и F равны и S, и сумма оценок; A выше по меньшей цене). В документе на ранговой шкале побеждал C; расхождение ожидаемо и объяснено на странице `/how`. Числа в таблице зафиксированы в `data/fixtures/balance_abcdef.toml` с допуском 0,05.

Для чего. Парето-фронт, допуски, ползунок по фронту и точка «колена» в фазе 2 используют те же `q_price` и `q_rating`; фронт считается по тем же значениям.

### 5.6 Объяснение «почему здесь»

Для каждого товара в выдаче генерируются до трёх фраз из фиксированного набора шаблонов с подставленными числами: «18% cheaper per mg than the category median», «rating 4.7 from 12,000 reviews», «formula changed in 2026». Шаблоны в `site/templates/why/*.txt`, ключи для локализации с первого дня.

## 6. Конвейер данных

Ежедневная задача `vitrina ingest && vitrina build && vitrina verify && vitrina publish`, запуск по расписанию в 06:00 UTC.

| Шаг | Что делает | Отказ |
| --- | --- | --- |
| `ingest` | Скачивает фид сети по URL из секрета, сверяет `iherb_id` с каталогом, пишет `PriceSnapshot` и, в ветке A, `RatingSnapshot`. Новые товары категории попадают в очередь `pending_labels` | Фид недоступен: снимок за день не создаётся, задача завершается с кодом 2, уведомление владельцу. Сайт не пересобирается |
| `build` | Считает `P_unit`, `R_b`, пресеты; генерирует HTML в `out/<date>/` | Товар без данных: страница с причиной; сборка продолжается |
| `verify` | Проверяет: число товаров с `P_unit` не упало больше чем на 20% ко вчерашнему; контрольный набор совпадает; все внутренние ссылки существуют; размер критического HTML и CSS в бюджете | Любая проверка не прошла: публикация не выполняется, код 3 |
| `publish` | Атомарно переключает `out/current` на новый каталог и загружает на хостинг | Ошибка загрузки: предыдущая версия остаётся |

Почему. Публиковать устаревшие цены хуже, чем не публиковать: на карточке стоит время обновления, и оно должно быть честным. Порог 20% ловит сломанный фид раньше пользователей.

Для чего. В фазе 2 к `ingest` добавляется расчёт медианы за 90 дней по накопленным снимкам; `verify` получает проверки истории.

Границы. `ingest` никогда не обращается к iherb.com. `build` не читает сеть.

## 7. Сайт

### 7.1 Маршруты и шаблоны

| Путь | Шаблон | Содержание |
| --- | --- | --- |
| `/c/<slug>?preset=balance` | `category.html` | Список товаров с ценой за единицу, рейтингом (ветка A), чипами «почему здесь», временем обновления, кнопкой покупки |
| `/pr/<slug>/<id>` | `product.html` | Разобранная этикетка с источником каждого числа, место в трёх пресетах, до пяти соседей по `balance`, кнопка покупки |
| `/pr/<slug>/<id>` для товара без данных | `product_pending.html` | «Added to the queue», ссылка на оригинал, `noindex` |
| `/how` | `how.html` | Формулы и контрольные числа раздела 5, источники данных, время обновления, как мы зарабатываем |
| `/disclosure`, `/privacy` | статические | Требуются для одобрения в сети |
| `/api/click`, `/api/report` | edge-api | Раздел 8 |

Почему пути повторяют iHerb: пользователь меняет домен в ссылке и попадает на ту же страницу. `slug` и `id` берутся из фида без изменений.

Для чего. В фазе 2 добавляются `/best/<category>` для поисковых страниц и `/compare?ids=`; они используют те же шаблоны карточек.

### 7.2 Бюджет производительности

Первая отрисовка на телефоне быстрее секунды при 4G: HTML страницы категории до 60 КБ, CSS до 30 КБ, JS до 10 КБ, без блокирующих запросов, изображения товаров лениво и только если фид разрешает их использовать. Проверка в `verify` по размеру файлов и в CI через Lighthouse на эмулированном телефоне.

Почему. Документ: «первая выдача открывается на телефоне быстрее чем за секунду»; большинство покупок с телефона.

### 7.3 Состояние в адресе

Пресет и, в будущем, фильтры живут в query-параметрах. Без JavaScript страница показывает пресет по умолчанию `balance` (ветка A) или `cheapest_per_unit` (ветка B); JavaScript переключает вкладки без перезагрузки, читая заранее отрисованные три списка.

Для чего. Ссылки-состояния в фазе 2 и стек в ссылке в фазе 3.

### 7.4 Локализация

Все строки интерфейса в `site/i18n/en.toml`, шаблоны обращаются по ключам. Валюта, формат чисел и направление письма выведены в настройки локали. В фазе 1 одна локаль `en-US`.

Почему. Порядок локализаций после английского: корейский, арабский, японский, иврит, китайский традиционный, португальский. Арабский и иврит требуют письма справа налево; закладывать это в CSS дешевле сейчас, чем переделывать.

Границы. Названия товаров и состав не переводятся: они с этикетки.

### 7.5 Кнопка покупки

Один компонент `buy_button.html`: трекинговая ссылка сети с `iherb_id` и параметром пресета в сабметке, если сеть поддерживает; текст раскрытия в том же блоке; `rel="sponsored nofollow"`; событие клика отправляется через `navigator.sendBeacon` до перехода.

## 8. edge-api

Решение. axum, один бинарник, SQLite, два маршрута: `POST /api/click` и `POST /api/report`. Ограничение частоты по IP: 60 запросов в минуту. Тело до 4 КБ. Ответ 204. IP не сохраняется; `session_hash` вычисляется на сервере из user agent и даты.

Почему. Единственные динамические действия в фазе 1: подсчёт кликов и приём сообщений об ошибках. Полноценный бэкенд не нужен.

Для чего. В фазе 2 сюда добавляются подписки на алерты; в фазе 3 бот использует тот же сервис для расчётов через `catalog-core`.

Границы. Никаких персональных данных. Никакой отдачи HTML из edge-api.

## 9. Хостинг и эксплуатация

| Компонент | Решение | Почему |
| --- | --- | --- |
| Статика | Cloudflare Pages или аналог за CDN | Первая отрисовка за секунду по всему миру; бесплатный уровень |
| edge-api и ежедневная задача | Один VPS в юрисдикции из И9 (например Hetzner в ЕС), systemd timer | Дёшево, один бинарник, полный контроль над логами |
| Секреты | Переменные окружения из файла вне репозитория | Ключ фида и токен хостинга не попадают в git |
| Резервные копии | Ежедневная копия SQLite и `data/` в объектное хранилище, 90 дней | История цен восстанавливаема |
| Мониторинг | Проверка: возраст последнего снимка меньше 36 часов, доступность `/c/<slug>`, доступность `/api/click`; уведомление владельцу в почту | Устаревшие цены обнаруживаются раньше пользователей |

Для чего. Фаза 2 добавляет второй крон (алерты); архитектура не меняется.

## 10. Правила работы агентов в репозитории

### 10.1 Шаблон ADR

Файл `docs/adr/NNNN-<slug>.md`:

```
# NNNN. Название
status: proposed | accepted | assumed | superseded by NNNN
date:
## Решение
## Почему (предпосылки)
## Для чего (будущее)
## Границы
## Что проверить, если предпосылка не подтвердится
```

Каждое отступление от этой спецификации оформляется как ADR со статусом `proposed` и ссылкой в PR. Решения из этой спецификации считаются ADR 0001–0012 и не переписываются без владельца.

### 10.2 Качество

| Требование | Как проверяется |
| --- | --- |
| `cargo clippy --all-targets -- -D warnings`, `cargo fmt --check` | CI на каждый PR |
| `catalog-core` собирается под `wasm32-unknown-unknown` | CI |
| Юнит-тесты конверсий на всех строках `data/reference/` | Тест генерируется из справочника |
| Property-тесты (`proptest`): рост цены не повышает `q_price`; рост рейтинга не понижает `q_rating`; порядок `balance` не зависит от порядка входа | `catalog-core` |
| Контрольный набор A–F из раздела 5.5 | `data/fixtures/balance_abcdef.toml` |
| Снимок HTML категории и товара на фикстуре | `insta` |
| Страница `/how` содержит те же контрольные числа, что и тест | `how_page_matches_code` |
| Бюджет размеров из 7.2 | `vitrina verify` и CI |

### 10.3 Процесс

1. Задача берётся из `docs/backlog.md`, у каждой указаны этап и зависимости от вопросов раздела 12.
2. Ветка на задачу, PR с описанием «что, почему, что проверено». Один PR не трогает больше одного крейта без причины, названной в описании.
3. Изменение любого файла в `data/reference/` требует ссылки на источник в самом файле и второго проверяющего.
4. Изменение `data/labels/` требует полей `verified_by` и `verified_at`.
5. Найденная в ходе работы неизвестная величина не додумывается: агент добавляет пункт в `docs/open-questions.md` и, если работа блокирована, останавливается.
6. Сообщения коммитов на английском, в настоящем времени, с указанием крейта: `catalog-core: add IU conversion for vitamin D`.
